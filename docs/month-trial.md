# 한 달 개인 검증 (n=1, 30일)

## 무엇을 판단하나

과거 생각을 다시 이어가는 이득이 검토·정정·관리·방해 복귀 비용보다 큰지
판단합니다. 한 사람의 관찰이므로 일반적 효과나 인과관계를 증명하지 않습니다.
코드 테스트 통과도 실제 한 달의 효용을 증명하지는 않습니다.

자동 자료 수집이나 LLM이 없는 규칙 기반 도구입니다. 직접 입력한 근거에
대한 연결·제안·침묵·수정 경험을 평가하며, 자동 발견력은 평가하지 않습니다.
iCal 일정 구독은 다음 달 실제 일정에 맥락 복원을 붙여 보는 선택 기능입니다.
구독하지 않아도 나머지 시험은 그대로 진행됩니다.

## 준비 (Day 0)

1. [README의 실행 절차](../README.md)를 따라 앱을 실행합니다.
2. 작업 영역 1~2개와 보류 중인 관심사 1개를 정합니다.
3. **내 기록 → 생각 기록**에서 종류를 관심으로 고릅니다. 내용,
   왜 중요한가, 현재 장애물, 적용 범위와 관심 알림 방식을 입력합니다.
4. **일정 → 구독 추가**에 이번 달에 실제로 쓰는 캘린더를 등록합니다.
   여러 개를 넣어도 되고, 일정이 몰리는 날의 맥락 복원 노력을 일지에 적습니다.
5. **설정**에서 조용 모드와 집중 시간을 정합니다. 범위별 선호는 기록의
   적용 범위 이름과 같아야 합니다. `global`은 공통 기본값입니다.
6. **기록 · 백업 → SQLite 스냅샷 생성**으로 초기 백업을 만듭니다.
   서버는 프로젝트 폴더에서 실행하세요. 스냅샷은 자동 삭제되지 않습니다.
   한 달 동안 초기 사본과 주간 사본을 보관하고 종료 후 직접 정리하세요.
   복사본을 별도 DB로 열어 확인하는 방법은 README의 복원 절차에 있습니다.
7. 비슷한 작업을 하는 기준선 날짜와 비서 사용 날짜를 3~5쌍 정합니다.
   작업 종류·분량·시간대·정보 노출량을 가능한 한 맞추고 일지 메모에 적습니다.

## 30일 일정

| 기간 | 하는 일 |
| --- | --- |
| Day 1~7 | 기준선. 기존 노트·검색 방식을 그대로 사용하고 일지만 기록 |
| Day 8~14 | 비서 사용. 관심과 출처를 입력하고 제안을 검토. 모호함·승인·침묵 시험 |
| Day 15~21 | 잘못된 기억과 선호를 정정. 다른 범위까지 바뀌지 않는지 관찰 |
| Day 22~29 | 오래된 관심 재발견, 취소·중단 후 행동, 놓친 기회를 확인 |
| Day 30 | 원시 기록과 비교 가능한 날짜 쌍을 검토해 계속/축소/중단 결정 |

주말이나 미사용일도 결과를 만들기 위해 억지로 채우지 않습니다.
유용한 변화가 없었다면 없었다고 기록합니다. 가상 진단은 실제 경험과
구분하여 일지 메모에 '가상 시험'이라고 표시하세요.

## 매일 남길 기록

**한 달 일지**에서 날짜와 기준선/비서 조건을 먼저 고릅니다.
같은 날짜·조건으로 저장하면 해당 기록을 갱신합니다.
저장 전 **이 날짜 기록 불러오기**로 이전 입력을 확인할 수 있습니다.

- 노력 6개(분): 맥락 복원, 검색, 작업 재시작, 검토·정정, 비서 관리,
  방해 후 복귀. 빈칸은 미측정이며 실제 0분일 때만 0을 입력합니다.
- 횟수 8개: 받은/수용한 기회, 놓친 중요 기회, 원치 않은 방해, 근거 오류,
  정정 횟수, 취소·중단 위반, 승인 경계 위반.
  현재 횟수는 정수이며 빈 값도 0으로 저장됩니다. **각 횟수를 확인한 뒤
  저장하세요.** 측정하지 못한 횟수는 메모에 '미측정: 항목명'으로 표시하고,
  그날의 0을 성공의 증거로 쓰지 마세요.
- 체감 4개(1~5): 유용성, 부담, 통제감, 신뢰. 빈칸은 미측정입니다.
- 메모: 비교할 작업, 놓친 기회, 제안을 수용/거절한 이유, 잘못된 기억,
  측정하지 못한 항목과 복구에 든 노력을 적습니다.

일지 작성 자체가 오래 걸리면 비서 관리 시간에 포함하고 입력 부담도 평가하세요.

## 기간 비교의 계산

```text
일일 총 노력 = 맥락 복원 + 검색 + 작업 재시작
             + 검토·정정 + 비서 관리 + 방해 후 복귀
앱 순절감(분/일) = 기준선 일일 총 노력의 중앙값 − 비서 조건의 중앙값
```

이 계산은 현재 `src/server/evaluate.ts`의 구현 기준입니다.
초기 설계 계약의 비대칭 합계식 대신 양쪽 조건에 동일한 6개 비용을 씁니다.

여섯 시간 항목이 모두 기록된 날만 순절감에 포함됩니다. 완전한 기준선 또는
비서 사용일이 없으면 순절감은 계산하지 않습니다. 화면의 '기준선 N일·비서
M일'은 **부분 입력까지 포함한 저장 일수**이지 계산에 포함된 완전한 일수가
아닙니다. 결측 일수는 JSON 내보내기의 원시 일지에서 직접 확인하세요.

앱의 기간 요약은 참고용입니다. 비교 가능한 날짜 쌍의 총 노력 차이를 별도로
계산하세요. 조건별 작업량·난이도 차이는 앱이 자동 보정하지 않습니다.
체감 평가의 API 통계는 중앙값이며 화면에는 표시하지 않습니다. 분포와 개별
평가는 내보낸 JSON에서 확인하고 평균으로 잘못 표기하지 마세요.

## 진단할 10가지 경험

| 유형 | 시험과 관찰 |
| --- | --- |
| 01 장기 맥락 | 이전 관심을 질문하고 원문·인용이 정확한지 확인 |
| 02 선호 변화 | 연구 범위의 알림을 바꾸고 글쓰기 범위는 유지되는지 확인 |
| 03 모호한 희망 | '언젠가'를 관심으로 저장. 약속·위임이 생기지 않아야 함 |
| 04 관심 간 연결 | 서로 다른 기록과 근거의 연결이 실제로 유용했는지 사람이 판단 |
| 05 유용한 기회 | 장애물을 해결하는 새 근거와 무관한 유사 키워드 자료를 비교 |
| 06 올바른 침묵 | 조용 모드/집중 시간에 보류되는지, 중요 기회를 놓치지는 않는지 기록 |
| 07 일정 변경 | 로컬 약속을 취소하고 재예약되지 않는지 확인. 외부 달력 연동은 없음 |
| 08 경계와 승인 | 수락만으로 약속이 생기지 않는지, 승격은 별도 선택인지 확인 |
| 09 창작 보조 | 확정 설정은 사실, 미정 구상은 가설로 저장. 결과가 구분하는지 확인 |
| 10 오류 회복 | 장애물·문장을 정정하고 과거 제안 만료와 향후 제안 반영을 확인 |

이 표는 모두 자동으로 해결한다는 약속이 아니라 개인 진단 항목입니다.
연결의 의미·새로움·창작 기여는 규칙 매처만으로 판단할 수 없습니다.

## 즉시 별도로 다룰 실패

취소·추적 중단 무시, 명시적 승인 없는 영향, 확정되지 않은 관심을 사실로
보고하는 문제는 시간 절감으로 상쇄하지 않습니다. 관련 제안을 중단하고,
원문·출처·이력을 보존한 뒤 무엇을 잘못 이해했는지 적으세요.
외부 발송·구매·실제 달력 변경 기능은 이 프로토타입에 없습니다.

## 월말 결정

**기록 · 백업**에서 JSON과 최종 SQLite 스냅샷을 남긴 뒤 다음을 정리합니다.

1. 저장 일수, 완전한 시간 측정 일수, 결측·미측정 항목.
2. 비교 가능한 날짜 쌍별 노력 차이와 6개 구성 비용.
3. 유용/무용/시점이 나빴던 제안, 놓친 기회와 그 이유.
4. 승인·중단·취소·근거 오류 사건과 복구 노력.
5. 체감 평가의 분포, 통제감, 앱 없이도 맥락을 설명할 수 있는지.

- **계속:** 중요한 경계가 지켜지고 순편익 또는 구체적인 판단 개선이 있음.
- **축소:** 특정 영역만 유용하거나 제안 검증·관리 부담이 큼.
- **중단:** 반복된 경계 위반, 오류 은폐, 순비용 또는 통제감 저하가 지속됨.

좋은 결론을 미리 정하지 마세요. 유용한 제안이 없었던 달도 유효한 결과입니다.
