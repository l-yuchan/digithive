## C1. 자식 작업이 사용량 한도 후에도 `running`으로 남는다 — #9711

- **상태**: open (2026-10-07 생성, 댓글 9). 라벨 없음.
- **문제**: 위임된 자식(senpi-task)이 턴 도중 제공자 사용량 한도에 걸리면 `running`에 머물고, 부모 세션은 이를 살아 있는 작업으로 계속 취급한다. 대체 모델이 있으면 다른 모델로 넘어가지만, 폴백 체인이 비었거나 소진되면 정산되지 않는다.
- **읽은 근거**: 본문 + 최근 댓글 2건.
- **원인 추적(유지보수자 코멘트)**: 엔진 쪽 수정 #11388("settle usage-limit turns in bounded time")이 #12926 폴백 열차에 실려 진행 중. 소비자 쪽 프로브(dev `7e0921df8a`)에서 "after a usage-limit `agent_end` with `willRetry true`, the settlement held the outcome and emitted nothing even once the session went idle, while `willRetry false` settled as error" — 즉 재시도 신호의 소유자가 엔진이고, 하네스는 그 신호를 기다리다 아무 이벤트도 내지 않는다.
- **교훈**: 작업 상태를 "마지막 이벤트가 오지 않음"에 의존해 두면 영구 미정산 상태가 생긴다. (a) 턴 종료는 시간 상한을 갖고, (b) 재시도 대기와 종료를 구분하는 상태(`retrying`/`settled`)가 필요하며, (c) 부모가 자식을 기다릴 때도 기한이 있어야 한다.
- **digithive 관련**: digithive에도 같은 모양의 위험이 있다. `runtime/queue.ts`의 실행 상태가 워커 이벤트에 의존하고, 클라이언트는 1초 폴링으로 종료를 확인한다(`apps/assistant/src/web/app.ts`). 워커가 죽어도 run이 `running`으로 남지 않도록 리스/하트비트 기반 회수가 필요하다.
- **미확인**: 실제 재현 조건(리포터 환경), 수정 PR의 최종 병합 여부.

## C2. 파일시스템 오류 하나로 자식이 영구 `pending` — #11269

- **상태**: open (2026-10-25, 댓글 2, 라벨 `bug`, `needs-triage`).
- **문제**: Windows에서 작업 레코드 rename이 EPERM으로 실패하면 자식이 `pending`에 영구히 남는다. 재시도 예산이 약 40 ms에 불과하다.
- **교훈**: 상태 전이를 단일 파일 연산에 걸어 두면 그 연산의 일시 실패가 영구 상태가 된다. Windows에서는 rename이 바이러스 스캐너·파일 잠금으로 흔히 실패한다. 상태 저장은 "의도 기록 → 재조정(reconcile)" 방식이어야 하고, 재시도 예산은 초 단위여야 한다.
- **digithive 관련**: 현재 스택은 Windows 개발 환경에서 개발되지만 운영은 Linux(`mini`) 컨테이너다. 그럼에도 SQLite 외 파일 기반 원자 연산을 상태 저장에 쓰지 않는 편이 안전하다.

## C3. 훅이 멈추면 세션이 영구 정지, Esc도 무효 — #14354

- **상태**: closed (2026-11-19 → 2026-11-22). 댓글 5.
- **문제**: PostToolUse 훅이 끝나지 않으면 세션 전체가 `Running PostToolUse hook (5m+)`에 갇히고, Esc가 듣지 않고, 타임아웃이 없으며, 훅이 in-process라 죽일 프로세스도 없다.
- **수정·검증**: #14356으로 `dev` 병합(`eea1c84bb5be9cd88c8124c3b5092737fdad9182`), 엔진 쪽은 senpi#7069(`b3078f50e0`). 설치본 `omo 5.1.81`에서 100 ms 데드라인으로 검증: `handler timed out after 102ms; the tool result continues without it` — 도구 결과는 훅 없이 모델로 전달되고 턴이 끝났다. 30 s 데드라인 실행에서 RPC `abort`가 훅 진입 2 ms 후 성공, 대화형 Esc도 `agent_end` 98 ms 내 관측.
- **교훈**: 확장 지점(훅·도구·이벤트 핸들러)에는 전부 데드라인과 중단 가능성이 필요하다. "훅이 실패해도 결과는 흐른다"가 기본값이어야 한다.
- **미확인**: 릴리스 반영 범위(검증은 5.1.81, 현재 설치본 5.1.65).

## C4. 기억 도구 호출이 1시간 27분 멈춤, Esc 무시 — #14543

- **상태**: closed (2026-11-21 → 2026-11-23). 댓글 1.
- **문제**: `memory` 도구가 도구 호출 abort 신호를 무시하고 전체 호출 데드라인이 없다. 하위 git 단계는 각각 제한(commit 120 s, 그 외 30 s, 락 5 s)되어 있으나 파일 읽기·쓰기·엔진 준비는 순수 await다. 현장 사례: TUI에 약 1시간 27분 "running" 표시, Esc/Ctrl-C 무효, 세션 SIGKILL.
- **원인**: 엔진의 Bun 풀이 멈춘 automount에서 고갈(senpi#7157, 모든 풀 스레드가 `realpath -> openat`에서 정지).
- **수정**: #14546 (초안). RED 테스트 `tools-call-bound.test.ts`가 base에서 exit 1, abort/deadline 케이스가 60 s 타임아웃까지 멈춤. GREEN에서 3/3 통과 + 관련 스위트 29/29, 118/118.
- **교훈**: C3과 같은 계열의 재발이다. 개별 도구 수정으로 끝내지 말고 **공통 호출 경계(데드라인 + abort 전파)** 를 한 곳에 두어야 한다.
- **digithive 관련**: digithive의 에이전트 실행도 도구 호출마다 상한이 필요하다. 현재 `agents/provider.ts`는 HTTP 타임아웃만 있고(`timeout: limits.timeoutMs`), 도구 실행 자체의 상한은 별도다.

## C5. 권한 거부가 도구 결과로 돌아오지 않아 턴이 영원히 실행 — #14649

- **상태**: open (2026-11-22, 댓글 12).
- **문제**: `permission_preset: "read-only"` 스레드의 첫 턴이 `write`를 호출하면 파일은 안 써지지만 모델에 거부 결과가 전달되지 않아 `state: "running"`에 남고, `thread_close({force:true})`로만 끝난다. 121 s / 276 s 두 번 측정.
- **수정 진행**: 엔진 senpi#7270이 4차 리뷰 후 `fc392c21b6`에서 게이트 대기. 회귀 테스트 `omo-14649-refused-approvals.test.ts`(main 14, worker 2) 추가. 이전 헤드 소스에서는 main 1 실패/13 통과, worker 2 실패 — 즉 테스트가 결함을 실제로 잡았다.
- **교훈**: **거부도 결과다**. 정책 차단 경로는 (a) 모델에 구조화된 도구 결과를 반환하고, (b) UI에 "거부됨" 상태를 남기고, (c) 턴을 정상 종료해야 한다. 승인 대기(`ask`)와 거부(`deny`)를 다른 상태로 모델링해야 한다.
- **digithive 관련**: digithive는 `awaiting_approval` 상태를 이미 모델링하고 있으나(`apps/assistant/src/runtime/queue.ts`, `web/app.ts`), 거부 응답이 실행 결과로 어떻게 반영되는지는 이번 조사에서 읽지 못했다(미확인).

## C6. 모델 스트림이 중간에 멈추면 턴이 정산되지 않음 — #14329

- **상태**: open (2026-11-19, 댓글 1).
- **문제**: TUI에서 모델 스트림이 답변 중간에 멈추면 "Working forever"로 남는다.
- **교훈**: 스트리밍에는 (a) 첫 토큰 타임아웃, (b) 토큰 간 유휴 타임아웃, (c) 명시적 `stream_error` 이벤트가 필요하다. 재연결 클라이언트는 마지막 수신 seq를 알고 그 이후만 받아야 한다.
- **미확인**: 원인(제공자/전송/하네스) 분류.

## C7. 중단 후 재개할 때 자식이 '사용자 정지'로 오인 — #11856

- **상태**: open (2026-10-30, 댓글 3). 대응 수정 #11859 "fix(omo-senpi): a reopened session's interrupted-run hold is not a user Stop" (open).
- **문제**: 턴 중간에 종료된 세션을 다시 열면, 대기 중이던 자식들이 재개되지 않고 일시정지된다. "중단된 실행을 붙잡고 있음(interrupted-run hold)"과 "사용자가 Stop을 눌렀음"이 같은 신호로 읽힌다.
- **교훈**: 취소 의도는 **누가 눌렀는지**를 담아야 한다(`user_cancel` / `host_restart` / `interrupted`). 복구 정책이 이 구분에 따라 달라진다.

## C8. 언어 정책이 툴 사용·압축 후 표류 — #11527, #12625

- **상태**: #11527 open (2026-10-27, 댓글 4, 라벨 `bug`), #12625 open (2026-11-06, 댓글 3).
- **문제**: 한국어 사용자에게 영어로 계속 답한다. 압축 이후나 도구 호출이 많은 턴에서 표류. #12625 제목에 "senpi#4540 is unmerged"가 언급되어 엔진 쪽 미병합 수정이 있음을 시사.
- **교훈**: 시스템 프롬프트 문구 한 줄로는 응답 언어가 유지되지 않는다. 압축 이후에도 남는 위치(세션 헤더, 매 턴 재주입되는 짧은 지시, 응답 후 검증)에 정책을 두어야 한다. digithive가 브리핑·대화 전반에서 한국어를 유지해야 하는 요구와 직접 연결된다.

## C9. 동기 서브에이전트의 진행이 부모에 스트리밍되지 않음 — #7288

- **상태**: open (2026-08-25), 라벨 `opencode`. 제목 `fix(delegate-task): stream sync subagent toolcall progress to parent while running`.
- **교훈**: 위임의 가시성은 "시작/종료" 두 이벤트로 충분하지 않다. 부모 대화에 자식의 도구 호출 진행이 흘러야 사용자가 멈출지 판단할 수 있다. 반대로 자식 이벤트를 부모 대화에 그대로 섞으면 맥락이 오염되므로, **부모 표시용 요약 이벤트**와 **자식 원본 이벤트**를 분리해야 한다.

## C10. 백그라운드 연속 작업이 멈추면 부모가 깨어나지 않음 — #14508

- **상태**: closed (2026-11-21), `fix(background): wake parents when continuation stalls`.
- **교훈**: "계속 진행"을 기대하는 구조(자동 계속, 재시도, 백그라운드 루프)에는 감시자가 필요하다. 감시자가 부모를 깨우는 경로가 없으면 조용히 멈춘다.

## 사례 종합: 반복되는 결함 계열

1. **정산되지 않는 상태** (C1, C5, C6, #14329) — 종료 이벤트가 오지 않을 수 있다는 전제가 없다.
2. **경계에 데드라인·중단 부재** (C3, C4) — 같은 계열이 두 번 재발했고, 두 번째는 수정 후보가 초안 단계다.
3. **거부·취소를 결과로 모델링하지 않음** (C5, C7) — 침묵이 상태를 만든다.
4. **파일시스템/외부 의존에 걸린 상태 전이** (C2) — 재조정 필요.
5. **하네스 수준 정책의 표류** (C8, #13016) — 프롬프트·진입점마다 다시 해석됨.
6. **가시성 부족** (C9, #14493) — 시작/종료 두 이벤트만으로는 판단할 수 없다.

이 여섯 계열은 digithive 설계 체크리스트로 그대로 쓸 수 있다(`architecture-options.md` §5).
