# digithive 하네스 재설계를 위한 조사 계획

작성일: 2026-11-24

상태: 검토용 계획안. 외부 조사 실행, 제품 구현, 기존 데이터 이전, 배포를 승인하거나 완료했다는 뜻이 아니다.

## 1. 목적과 이번 문서의 범위

digithive를 사용자가 일상적으로 대화하고 복잡한 작업을 맡길 수 있는 완성형 에이전트 하네스로 발전시키기 위해, 주요 하네스의 실제 구현과 발전 과정을 광범위하게 조사한다. 조사 결과를 근거로 제품 요구와 구조적 선택지를 정리하고, 다음 단계의 방향을 가볍게 제안한다.

현재 최소 구현의 유지에 얽매이지 않는다. 필요하다면 대화 UI와 하네스를 새로 만드는 선택까지 비교한다. 다만 전면 재작성 자체를 목표로 정하거나 기존 코드의 재사용을 미리 배제하지 않는다.

이번 계획의 중심 산출물은 조사 보고서와 설계 선택의 근거다. 상세 구현 명세, 파일별 변경 목록, 구현 일정, 개발용 작업 분해는 조사 결론과 사용자 검토 이후에 작성한다.

현재 문서 작성에서는 외부 하네스 조사를 시작하지 않는다. 계획 요약을 사용자가 검토하고 조사 착수를 승인한 뒤 실행한다. 조사 완료 후에도 구현·배포는 별도 승인을 받는다.

## 2. 확정 요구와 계획 단계의 미정 사항

### 2.1 사용자 요구

- OmO, OpenCode, Codex처럼 풍부한 실행 기능과 사용 경험을 갖춘 하네스를 지향한다.
- 스트리밍 응답, thinking 영역, 도구 호출과 결과, 진행·실패 과정을 사용자가 확인할 수 있어야 한다.
- 대화 제목 변경·삭제, 메시지 수정, 분기 등 기본적인 대화 관리 기능을 포함한다.
- Enter는 전송, Shift+Enter는 줄바꿈으로 동작한다. 한글 조합 중 Enter를 전송으로 오인하지 않는다.
- 시스템 프롬프트와 맥락 구성을 재검토한다. 날짜를 메일 등에서 추론하게 두지 않고 신뢰할 수 있는 현재 날짜·시각·시간대를 제공한다.
- UI 프레임워크 도입과 MVP 이상 수준의 코드베이스 구조를 검토한다.
- OmO 등의 실제 코드와 이슈·PR을 핵심 자료로 삼는다.
- 사용자와 직접 대화하는 에이전트·하네스와 백그라운드에서 복잡한 작업을 수행하는 에이전트·하네스를 구별해 조사한다.
- 두 역할에 하나의 하네스를 공유할지, 별개로 만들지, 공통 모듈을 둘지 근거를 통해 결정한다.
- 조사에 비중을 두고 구현은 가벼운 제안으로 한정한다.

### 2.2 유지할 제품 맥락

개인용 단일 사용자 비서이며, 별도 서버에서 실행하고 PC·모바일로 접근한다. 대화, 위임 작업, 예약 자동화와 브리핑, 개인 자료 연결, 기억과 파일을 함께 다룬다. 반복 확인은 스크립트가 충분하면 스크립트를 우선한다.

외부 행동과 운영 환경 변경은 명시적 승인 경계를 유지한다. 개인화 기억이 도구 권한이나 정책을 임의로 넓히지 않게 한다. 월 API 비용 약 USD 100이 부담 기준이라는 점을 선택지 평가에 반영한다.

이번 고도화는 여러 사용자용 서비스 확장이나 효과의 일반화 검증을 요구하지 않는다. 기능 검증과 한 사람의 실제 사용 편익은 구별한다.

### 2.3 조사 후 결정할 사항

아키텍처, UI 프레임워크, 실행 라이브러리, 모델·공급자, 저장·이벤트 방식, 멀티에이전트 구성, 기존 구성의 유지·교체 범위는 미정이다. 앞선 대화에서 나온 React 추천도 확정 결정이 아닌 비교 대상이다.

## 3. 사전 점검에서 보강한 사항

계획 작성을 막는 사용자 결정은 없다. 다만 다음 항목을 조사 계약에 추가해야 결과를 설계 판단으로 사용할 수 있다.

| 보강 항목 | 필요한 이유 | 처리 |
|---|---|---|
| 대상의 정확한 식별과 시점 | OmO 등 제품명·포크·기반 엔진·확장 계층을 혼동하지 않아야 함 | 공식 출처, 저장소, 버전·커밋, 조사일 기록 |
| 공개 수준과 근거 구분 | 공개 문서나 화면만으로 비공개 내부 구현을 단정할 수 없음 | 코드 관찰·실행 관찰·공식 설명·가설 분리 |
| 반대 근거와 회귀 사례 | 인기 기능이나 병합된 PR만 보면 유지 비용을 놓침 | 재발·revert·후속 수정·미해결 문제 추적 |
| 코딩 하네스와 개인 비서의 차이 | 터미널·저장소 중심 설계가 모바일·예약 작업에 그대로 맞지 않을 수 있음 | 개인 비서 시나리오로 전이 가능성 평가 |
| 재사용 가능성 | 기술적으로 쓸 수 있어도 라이선스·인증·배포 제약이 다를 수 있음 | 채택·임베드·포크·재구현의 조건 비교 |
| 데이터 수명과 소유권 | 편집·분기·삭제·기억·실행 중 지시가 서로 영향을 줌 | 책임과 상태 전이를 별도 조사 |
| 조사 종료 조건 | extensive 조사가 끝없는 자료 수집이 되지 않게 함 | 핵심 질문별 근거와 미해결 사항으로 완료 판단 |

## 4. 조사 대상과 자료의 우선순위

### 4.1 핵심 대상

| 대상 | 중점 |
|---|---|
| OmO | 시스템 지시 조립, 도구·Skill·확장, 작업 위임, 백그라운드 실행, 상태 전달, 개발·회귀 과정 |
| OpenCode | 세션·메시지·도구 모델, 실행 루프, 스트리밍, 권한, 클라이언트·서버 경계, 편집·분기 |
| Codex | 상호작용과 장시간 작업, 실행·승인·격리, 세션·이벤트 프로토콜, 클라이언트 연결 구조 |
| Claude Code 등 보완 대상 | 다른 접근을 비교하는 데 필요한 공개 문서·SDK·실제 동작·공개 이슈 |

이는 조사 항목이며 각 제품이 해당 기능을 제공한다는 사전 판정이 아니다. OmO의 공식 저장소와 기반 엔진의 관계부터 확인한다. 이름이 유사한 별도 프로젝트의 구현을 같은 대상으로 합치지 않는다.

보완 대상은 핵심 대상이 답하지 못한 질문이나 구조적으로 다른 대안이 있을 때 추가한다. 단순 제품 나열을 늘리는 데 조사 시간을 쓰지 않는다.

### 4.2 자료 수집 방식

1. 공식 저장소·문서·배포 정보를 확인하고 조사 기준 버전·커밋을 고정한다.
2. 주요 진입점부터 모델 입력, 도구 실행, 저장, 이벤트 전달, 화면 표시까지 실제 코드 경로를 추적한다.
3. 관련 테스트를 읽어 의도된 계약과 실제 구현을 대조한다.
4. 이슈·PR·변경 이력에서 설계 이유와 장애·회귀·대안의 흔적을 찾는다.
5. 코드만으로 판단하기 어려운 핵심 동작은 허용된 격리 환경에서 최소 재현한다.
6. 결과를 digithive 요구와 대조하고 반대 근거를 확인한 뒤 권고안을 작성한다.

조사 중 운영 코드나 설정을 변경하지 않는다. 공개 자료 수집은 읽기 중심으로 수행한다. 실험에 유료 호출·새 자격증명·외부 전송이 필요하면 목적과 예상 비용·자료 범위를 먼저 제시한다. 개인 메일·일정·LMS 데이터 대신 합성 자료로 시작한다. 이슈·PR에 글을 게시하지 않는다.

## 5. 조사할 핵심 축

| 축 | 답해야 할 질문 | 필요한 증거 |
|---|---|---|
| 실행 루프와 모델 어댑터 | 도구 호출, 긴 출력, 컨텍스트 한도, 공급자 차이와 오류를 어떻게 다루는가? | 요청·응답 변환, 루프, 테스트 |
| 스트리밍과 실행 가시성 | 답변·reasoning·도구 인자·결과·실패가 어떤 이벤트로 저장되고 전달되는가? | 생산부터 화면까지의 경로, 재연결 동작 |
| 대화와 입력 UX | 편집·분기·재생성·삭제·검색·초안·첨부·스크롤을 어떻게 처리하는가? | 데이터 구조, UI, 관련 테스트 |

| 작업 위임과 복구 | 위임·진행 보고·개입·취소·재시작·검증은 어떤 계약으로 연결되는가? | 작업 상태, 저장·복구, 오류·회귀 사례 |
| 도구와 확장 | Skill·스크립트·플러그인·MCP 등의 발견·등록·버전·권한은 어떻게 관리되는가? | 등록·호출·승인 경로, 확장 계약 |
| 권한과 격리 | 승인 대상과 인자 변경, 외부 자료의 지시, 비밀값, 실행 격리를 어떻게 통제하는가? | 정책 집행 지점, 위반 방지 테스트 |
| 기억과 자료 수명 | 기억 정정, 파일 버전, 출처, 삭제가 실행과 분기 맥락에 어떻게 반영되는가? | 식별자·계보·참조·삭제 정책 |
| 운영과 비용 | 동시성·예산·관찰 가능성·버전 변경·장애 복구 비용은 무엇인가? | 제한·과금·로그·배포 경로 |
| UI 기술과 코드 구조 | 역할·도메인·실행·전달·화면이 어떻게 분리되는가? | 의존 방향, 공개 계약, 클라이언트 구현 |

Thinking 영역은 공급자가 실제로 공개하는 reasoning 또는 요약의 범위와 지원 여부를 조사한다. 표시할 수 없는 내부 사고를 복원하거나 가짜 활동을 생성하는 기능으로 정의하지 않는다. 도구 기록의 비밀값 제거와 상세 결과 접근 범위도 함께 검토한다.

시스템 프롬프트는 문구뿐 아니라 조립·갱신·버전 관리와 검증을 조사한다. 코딩용 지시를 그대로 복제하지 않고 개인 비서의 대화·위임·승인에 적합한지 평가한다.

## 6. 두 역할의 관계를 결정하는 독립 조사

### 6.1 역할과 공유 여부를 분리해 판단

대화 역할은 사용자 의도·맥락 파악, 빠른 응답, 작업 위임, 승인과 결과 설명을 맡는다. 작업 역할은 특정 목표에 대한 조사·계획·도구 실행·검증·산출물 생성을 맡는다. 이는 비교를 위한 초기 책임 구분이며 실제 경계는 조사 결과로 정한다.

코드 공유와 실행 인스턴스 공유는 별개의 결정이다. 같은 코어를 쓰면서도 세션·프로세스·큐·저장소·권한·모델·예산을 분리할 수 있다. 반대로 별도 하네스가 같은 저장소를 사용할 수도 있다. 각 차원을 따로 기록한다.

| 대안 | 검토할 이점 | 확인할 부담 |
|---|---|---|
| 하나의 강력한 하네스 공유 | 도구·정책·기록의 일관성, 구현 중복 감소 | 대화 지연, 맥락 오염, 권한·장애 격리, 역할별 요구의 충돌 |
| 완전히 별개의 하네스 | 역할별 최적화와 독립 운영 | 중복 구현, 상태 불일치, 인계·승인·결과 연결 비용 |
| 공통 모듈과 역할별 실행 계층 | 기반 재사용과 역할 분리 | 공통 계약의 복잡성, 버전 결합, 추상화의 유지 비용 |

세 대안의 비교를 끝내기 전에 결론을 내리지 않는다. 모듈러 구조를 절충안이라는 이유로 추천하지 않는다. 기존 하네스를 한 역할에만 채택하거나 두 역할에 다르게 채택하는 선택도 비교한다.

### 6.2 반드시 정리할 경계

- 사용자 요청과 목표의 소유자, 완료 여부의 판정 주체.
- 위임 시 전달할 목표·자료·권한·예산·완료 조건.
- 진행 이벤트와 결과·오류의 전달, 순서·중복·재연결 처리.
- 실행 중 질문·승인·지시 변경·취소를 해당 작업에 연결하는 방식.
- 대화 편집·분기·삭제·기억 정정이 이미 실행 중인 작업에 미치는 영향.
- 동시 작업 간 자료·승인·예산 격리와 자원 경합.
- 클라이언트 종료·서버 재시작·작업자 장애 이후의 상태와 재개.
- 결과 파일·출처·검증 증거의 인계와 사용자에게 제시할 요약.
- 모델이 판단할 부분과 스크립트·정책 코드가 보장할 부분.

## 7. OmO 중심 이슈·PR 심층 조사

OmO에는 별도 조사 비중을 둔다. 사용자가 지적한 빠른 자동화 개발 과정에서 드러나는 실제 장애와 설계 수정을 추적한다. 특정 개발 방식이 우수하다는 결론은 전제하지 않는다.

각 핵심 조사 축에서 관련 문제를 검색하고, 다음 연결을 가능한 범위까지 읽는다.

`문제 보고 → 재현 조건 → 원인 → 논의된 대안 → 수정 diff·테스트 → 병합·릴리스 → 후속 회귀·되돌림`

최신·인기 이슈만 보지 않는다. 병합된 수정, 열린 문제, 거절·종료된 제안, 되돌린 변경을 포함해 반대 근거를 찾는다. 특히 장시간 정체, 상태와 산출물 불일치, 이벤트 누락, 취소·복구, 승인 우회, 맥락 손실, 비용 증가 사례를 조사한다.

사례마다 식별자, 상태, 날짜, 관련 커밋·버전, 재현·시험 여부, 남은 문제와 digithive에 주는 교훈을 기록한다. 이슈의 보고나 PR 병합만으로 현재 버전의 결함·해결을 단정하지 않는다. 읽지 못한 내용과 후속 확인이 없는 내용은 미확인으로 남긴다.

핵심 대상 사이에 코드를 공유하거나 포크 관계가 있으면 독립된 증거로 중복 계산하지 않는다.

## 8. digithive 기준 시나리오와 격차 분석

현재 서비스의 실제 코드·배포 버전부터 확인한다. 작업 폴더의 과거 프로토타입이나 예전 명세를 운영 v2의 현재 상태로 간주하지 않는다. 사용자 보고, 코드 관찰, 실행 관찰을 구분해 기준선을 기록한다.

| 시나리오 | 관찰할 내용 |
|---|---|
| 현재 날짜와 오늘 일정을 질문 | 신뢰할 수 있는 시간대·현재 시각, 출처의 발송일·수집일 구별 |
| 메일·LMS 자료로 조사와 초안 위임 | 맥락 수집, 실행 기록, 출처·파일·검증 연결 |
| 긴 작업 중 별도 질문 | 대화 응답성과 작업의 독립 진행 |
| 실행 중 수정·취소·추가 질문 | 지시의 대상, 반영 시점, 이미 발생한 효과 |
| 승인 대기 중 재접속 | 승인 대상·인자·유효성, 중복 실행 방지 |
| 스트리밍 중 연결 단절·새로고침 | 누락·중복 없는 복원, 저장된 결과와 화면 일치 |
| 메시지 편집·분기·재생성 | 경로별 맥락, 원본 보존, 결과·실행의 계보 |
| 대화 삭제와 기억 정정 | 연결된 작업·파일·기억의 수명과 참조 처리 |
| 서버 재시작·도구 실패·한도 도달 | 원인·중간 결과·재개 가능 범위의 가시성 |
| 모바일에서 입력·결과 확인 | 한글 조합, Enter·Shift+Enter, 초안 보존, 스크롤·접근성 |
| 예약 작업과 사용자 작업 동시 발생 | 우선순위, 자원·예산 경합, 알림과 결과 인계 |

동일한 합성 시나리오와 조건을 사용해 비교한다. 제품별로 실행할 수 없는 항목은 지원 안 됨과 미검증을 구별한다. 공급자·모델 차이가 큰 결과를 하네스 성능 차이로 단정하지 않는다.

사용자 데이터에 접근하지 않고 답할 수 있는 구조 질문부터 조사한다. 실제 계정·기기 검증이 필요한 항목은 후속 검증 조건으로 분리한다. 이 비교는 개인 제품의 설계 판단을 위한 것이며 일반 성능 순위나 벤치마크로 발표하지 않는다.

## 9. 기술 선택의 평가 방법

먼저 필수 조건을 확인한 뒤, 통과 가능한 대안을 같은 표에서 비교한다. 근거 없는 합산 점수로 결론을 만들지 않는다.

필수 조건은 서버 독립 실행, PC·모바일 접근, 과정·실패 가시성, 작업 지속성, 승인 집행, 개인 자료 보호, 비용 통제다. 조건별로 지원·부분 지원·미지원·미확인을 기록하고 근거를 연결한다.

그다음 다음 기준으로 장단점을 비교한다.

- 사용자 응답성과 장시간 작업의 신뢰성.
- 대화·위임·기억·브리핑 통합의 적합성.
- 실제 유지보수 비용, 코드 복잡성, 테스트와 진단 가능성.
- 공급자 교체와 저비용 모델의 도구·스트리밍 호환성.
- 기존 데이터·연동의 이전 비용과 되돌릴 수 있는 범위.
- 라이선스·재배포·서비스 이용 조건, 인증과 배포 제약.
- 업스트림 변경 추종, 포크 유지, 의존성 결합과 이탈 비용.

### 9.1 하네스 확보 방식

기존 하네스 채택·확장, 실행 코어·프로토콜 재사용, 자체 구축을 비교한다. 비공개 구현은 재사용 가능하다고 가정하지 않는다. 각 방식이 두 역할에 어떻게 적용되는지 함께 제시한다.

### 9.2 UI 프레임워크와 구조

현 DOM 방식 유지, React 계열, Svelte 계열, 서버까지 포함하는 앱 프레임워크를 비교 대상으로 둔다. 구체적인 후보·버전은 조사 시 공식 문서와 유지 상태를 확인한다.

스트리밍 상태, 메시지 분기·편집, 실행 기록, Markdown·코드·파일 표시, 접근성·모바일·한글 입력, 테스트 용이성, 기존 서버와의 결합 비용을 기준으로 판단한다. 컴포넌트 라이브러리·라우팅·서버 상태 관리는 프레임워크와 구분해 평가한다.

코드 구조는 폴더 이름부터 정하지 않는다. 도메인 규칙, 실행기, 모델 어댑터, 이벤트·API, 저장, 웹 클라이언트의 책임과 의존 방향을 먼저 정리한다. 현 구조의 보존·교체 근거를 함께 남긴다.

## 10. 조사 순서와 산출물

각 단계는 앞선 결과를 이용한다. 조사 착수 시 일정·비용 추정과 자료 접근 제한을 먼저 기록하고, 조사 범위가 크게 늘어나면 이유와 필요한 자원을 제시한다. 광범위한 조사와 무제한 유료 실험을 동일시하지 않는다.

| 단계 | 작업 | 종료 조건 |
|---|---|---|
| A. 기준선·대상 확정 | digithive 상태, 요구, 공식 대상·버전, 접근 가능 자료 확인 | 기준선과 출처 목록, 공개 범위·제약 명시 |
| B. 구현·UX 조사 | 핵심 축별 코드 경로·테스트·동작 추적 | 각 축에 근거 또는 접근 불가 사유 기록 |
| C. 이슈·PR 추적 | 원인·수정·회귀와 설계 대안 조사 | 주요 결론의 반대 근거와 해결 상태 확인 |
| D. 대안·시나리오 비교 | 두 역할, 확보 방식, UI·구조, 격차 분석 | 동일 기준 비교와 필요한 최소 재현 완료 |
| E. 종합·검토 | 권고안, 불확실성, 가벼운 후속 제안 작성 | 아래 완료 기준 충족, 사용자용 요약 제시 |

결과는 조사 착수 후 `docs/harness-research/` 아래에 작성하는 것을 제안한다. 아래 파일은 예정 산출물이며 현재 존재하거나 완성된 자료가 아니다.

| 예정 파일 | 내용 |
|---|---|
| `report.md` | 핵심 결론, 제품별 관찰, 근거 연결, 권고안과 남은 질문 |
| `sources.md` | 공식 대상·버전·커밋, 조사일, 출처·위치, 공개 범위, 조사 경로 |
| `case-studies.md` | OmO 중심 이슈·PR 사례와 원인·수정·회귀 연결 |
| `comparisons.md` | 하네스·역할 구조·확보 방식·UI 후보의 비교, digithive 격차 |
| `architecture-options.md` | 책임·소유권 표, 대안별 위임·이벤트·복구 흐름, 선택 이유 |
| `validation.md` | 재현 조건·명령·관찰 결과, 미실행 항목과 이유 |
| `summary.md` | 사용자가 승인 여부를 판단할 최종 요약과 가벼운 구현 제안 |

각 핵심 주장은 코드 경로·커밋·이슈·PR·공식 문서·실험 기록으로 추적 가능하게 한다. 근거 기록에는 관찰 내용, 버전·시점, 해석, 반대 근거, 검증 수준을 구분한다. 동적 링크만 남겨 나중에 무엇을 읽었는지 잃지 않도록 커밋과 필요한 인용 위치를 보존한다.

## 11. 조사 완료 기준

다음 조건이 모두 충족되면 조사를 종료한다.

1. OmO·OpenCode·Codex의 정확한 대상과 기준 버전을 확인하고 공개 자료의 한계를 명시했다.
2. 핵심 조사 축마다 실제 코드·동작 근거가 있거나, 확인할 수 없는 이유와 설계에 미치는 영향을 기록했다.
3. OmO의 관련 이슈·PR을 문제·원인·수정·후속 상태까지 추적했으며, 주요 결론에 대한 반대 사례를 찾았다.
4. 두 역할의 세 구조 대안을 같은 기준으로 비교하고 코드·인스턴스·상태·권한 공유 여부를 따로 설명했다.
5. 기존 하네스 채택·재사용·자체 구축과 UI 후보를 비교한 뒤 권고안과 선택하지 않은 이유를 제시했다.
6. 결정에 중요한 불확실성은 최소 재현으로 확인했거나, 미검증 상태와 후속 확인 조건을 명시했다.
7. digithive 요구와 관찰된 현재 상태의 격차, 기존 데이터·연동의 유지·이전 영향을 정리했다.
8. 최종 권고의 근거가 추적 가능하며, 구현 제안과 확인된 사실이 구별되어 있다.
9. 최종 요약에 사용자 결정 사항, 남은 위험·한계, 실제 조사 비용과 미실행 검증을 제시했다.

자료 수·제품 수·읽은 PR 수를 채웠다는 이유로 완료하지 않는다. 추가 탐색이 주요 선택을 바꾸는지 확인하고, 새로 열린 핵심 질문을 해결하거나 미해결로 명시한 뒤 종료한다. 접근 불가·비공개·미지원은 서로 구분한다. 핵심 판단을 막는 불확실성이 남으면 권고를 확정하지 않고 무엇이 필요한지 제시한다.

## 12. 조사 이후의 가벼운 구현 제안

현재 허용할 구현 제안의 깊이는 다음까지다.

- 권장 구조와 이를 선택한 이유.
- 유지·교체·재사용할 구성 요소의 대략적인 경계.
- 첫 적용 후보와 기대 효과, 주요 의존성.
- 데이터 이전·병행 운영·되돌림이 필요한 지점.
- 후속 상세 계획에서 정할 항목과 사용자 결정 사항.

예시 방향은 실행 기록·스트리밍과 현재 시각 주입, 대화 관리, 역할별 실행 구조, UI 전환이다. 이는 순서나 기술 선택의 확정이 아니다. 조사에서 더 적절한 접근이 확인되면 수정한다.

조사 결과를 근거로 구현을 자동 시작하지 않는다. 조사 보고서와 최종 요약을 사용자에게 제시한 뒤, 선택한 방향의 상세 구현 계획과 승인 범위를 별도로 정한다.

## 13. 기존 문서와의 관계

`assistant-v2-spec.md`는 기존 제품 목적과 요구의 참고 문서다. 이 문서의 상세 진행 화면 후순위 등 과거 범위는 이번 대화에서 요청한 하네스·UX 조사 목표를 제한하지 않는다. 반대로 과거 명세의 미정 상태를 운영 서비스의 현재 상태로 간주하지 않는다.

이번 문서는 그 명세를 덮어쓰거나 새 구현 계약으로 대체하지 않는다. 실제 조사의 결론과 사용자 결정이 나온 뒤 필요한 문서만 갱신한다.
