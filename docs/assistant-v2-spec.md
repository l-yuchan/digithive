# digithive v2 구현 명세 초안

작성일: 2026-11-22

상태: 논의 내용을 구현 가능한 계약으로 정리한 초안. 구현 완료나 배포 승인을 뜻하지 않는다.

작업 브랜치: `assistant-v2`

## 1. 목적과 문서의 권위

대화를 통해 개인 맥락을 기억하고, 일정과 정보를 연결해 준비할 일을 알려주며, 위임받은 조사와 문서 작업을 서버에서 수행하는 개인 비서를 만든다. 실제 사용과 피드백을 통해 발전시킬 수 있는 기반이 첫 결과물이다.

이 문서의 **확정 요구**는 이번 대화에서 사용자가 표현한 기대다. **제안**은 구현을 진행하기 위한 초안이며 사용자 결정과 구분한다. **미정**은 사용 정보 또는 추가 판단이 필요한 사항이다.

기존 프로토타입의 구조를 전제로 하지 않고 새로 구현한다. 기존 코드는 참고 자료로 남기며 이 명세 작성 단계에서는 삭제하지 않는다. 기존 데이터의 자동 이전은 아직 요구되지 않았으므로 별도 결정한다.

`../persistent_cognitive_assistant_research_note_2026-11-23.md`는 개념과 문헌의 참고 자료다. 문서의 날짜·체크리스트·과거 구상을 이번 프로젝트의 일정이나 필수 요구로 승격하지 않는다. 특히 Git Blackboard, 고정 역할 체계, 특정 기억 스키마, 연구 평가 체계를 필수로 삼지 않는다.

| 자동화 | 스크립트와 AI를 모두 사용. 반복 확인 작업을 매번 모델 호출로 처리할 필요 없음 |
| 진행 화면 | 상세 시각화는 후속 범위. 작업과 자료, 완료 상태를 보여주는 구상은 유지 |

## 3. 첫 버전의 사용 시나리오

### 3.1 아침과 저녁 브리핑

07:30에는 오늘 일정, 다가오는 과제·마감, 관련 자료, 준비할 일을 제시한다. 21:00에는 새 변경, 진행 중인 위임 작업, 내일 준비할 일을 제시한다. 수행 여부를 모르는 사용자 활동은 미완료로 단정하지 않는다.

각 항목은 원본 일정·메일·LMS 항목 또는 내부 파일로 연결한다. 확정 정보, 추출 후보, 비서의 제안을 구분한다. 관심 정보는 짧게 덧붙이고 발견한 내용이 없으면 생략한다.

조회 실패는 “일정 없음”과 구별한다. 브리핑에 출처별 마지막 성공 확인 시각과 확인하지 못한 범위를 표시한다. 일부 출처가 실패해도 확보한 자료로 브리핑을 만들되 최신 확인이 된 것처럼 표현하지 않는다.

### 3.2 변경 감지와 긴급 알림

동일 과제의 마감이 앞당겨지면 기존 마감과 변경된 마감, 근거를 연결한다. 다음 브리핑 이전에 대응해야 하는지 판단해 긴급 푸시 또는 다음 브리핑으로 보낸다.

동일 사건의 반복 조회는 새 사건을 생성하지 않는다. 내용이 실질적으로 변경되면 갱신으로 기록한다. 같은 변경을 여러 출처에서 발견해도 중복 알림을 줄인다. 해결되거나 철회된 변경에 대한 예정 알림은 재평가한다.

### 3.3 메일에서 일정과 작업 후보 추출

Gmail의 메일에서 날짜, 요청, 기한, 관련 인물과 자료를 추출한다. “다음 주쯤 만나자”와 확정된 약속을 구분한다.

메일에서 발견했다는 이유만으로 캘린더를 수정하거나 답장을 보내지 않는다. 명확한 정보는 출처와 함께 안내하고, 모호한 내용은 후보로 제시한다. 일정 등록·메일 발송 등 실제 외부 변경은 구체적인 승인 이후 수행한다.

### 3.4 대화에서 위임 작업으로

“이 과제 자료를 찾아 초안을 만들어줘”라는 요청을 받으면 관련 LMS 요구사항·일정·내부 자료를 가져와 조사하고 초안을 작성한다. 설명과 근거는 대화로 제공하고 파일은 내부 경로로 안내한다.

사용자는 진행 상태를 확인하고 취소하거나 추가 지시를 줄 수 있다. 에이전트 실행 종료와 요청 목표 달성을 구분한다. 자료 접근이 막히거나 일부만 끝났다면 결과와 남은 부분을 명시한다.

일상 질문은 필요 이상으로 작업을 쪼개지 않고 바로 답할 수 있어야 한다.

### 3.5 기억과 정정

대화에서 선호, 진행 중인 일, 관련 사실과 잠정적 관심사를 자동으로 추출한다. 원문, 요약, 추론을 구분하고 근거를 보존한다.

“그건 예시였어”, “지금은 다른 주제를 하고 있어”라는 정정은 이후 검색과 브리핑에 반영한다. 관심 표명을 위임으로 바꾸지 않는다. 기억 조회·정정·삭제 경로를 제공하고 삭제된 내용은 활성 검색과 파생 요약에서 제외한다. 백업의 보존·삭제 정책은 따로 명시한다.

### 3.6 도구와 작업 방식 개선

반복되는 자료 변환이나 조사 절차에서 병목을 발견하면 스크립트·Skill·하네스 변경안을 만들 수 있다. 변경 이유, 영향 범위, 시험 결과, 되돌리는 방법을 사용자에게 제시한다.

자동 작성과 격리된 시험을 허용하는 방향을 제안한다. 운영 작업 환경에 새 도구를 등록하거나 기존 도구·Skill·코드를 바꾸는 적용 단계는 승인 후 수행한다. 승인받지 않은 생성 코드를 예약 실행에 연결하지 않는다.

## 4. 책임과 실행 구조

다음은 구현 구조의 제안이다. 특정 프레임워크의 채택을 확정하지 않는다.

| 구성 요소 | 책임 |
|---|---|
| 웹 클라이언트 | 대화, 작업 상태, 파일, 기억 점검, 승인, 알림 설정 |
| 서버 | 인증, 대화·작업 API, 파일 접근, 모델·연동 자격증명 관리 |
| 스케줄러 | 주기·시각·이벤트 조건에 따라 실행 요청을 영속적으로 등록 |
| 실행기 | 스크립트와 에이전트 실행, 상태·출력·취소·시간·비용 관리 |
| 연동 어댑터 | 외부 변경 수집, 커서 관리, 공통 사건으로 정규화 |
| 기억·검색 | 출처와 정정 이력을 보존하고 관련 맥락 구성 |
| 브리핑·알림 | 정보 선별, 브리핑 저장, 긴급성 판단, 푸시 전송 |
| 정책 검사 | 데이터 접근 범위, 외부 행동, 환경 변경, 승인·예산 검사 |

개인용 단일 사용자, 파일 저장소와 SQLite 기반 메타데이터를 첫 구현의 출발점으로 제안한다. 서버와 실행기는 한 서버에서 시작하되 논리적 책임을 나눈다. 언어·UI 도구·실행 라이브러리는 구현 착수 때 결정한다.

에이전트 작업에는 목적에 맞는 도구를 제공한다. 초기 필수 도구 범위는 정보 검색·페이지 읽기, 내부 파일 읽기·작성, 승인된 스크립트 실행, 연결된 개인 정보 조회다. 검색 제공자와 동적 페이지 접근 방식은 구현 시 선정한다.

## 5. 스크립트와 에이전트를 함께 다루는 자동화

### 5.1 실행 정의와 실제 실행을 분리

`AutomationDefinition`은 언제 무엇을 수행할지 정의한다. `Run`은 그 정의로 실제 수행된 한 번의 실행이다. 즉시 요청도 같은 실행 기록을 사용하며 예약 정의가 반드시 필요하지는 않다.

| 정의 필드 | 의미 |
|---|---|
| id / version / enabled | 안정적 식별자, 버전, 실행 여부 |
| trigger | 정기 시각, 간격, 사건 또는 수동 실행 |
| timezone | 정기 시각의 기준 시간대 |
| executor | `script` 또는 `agent` |
| executor_ref | 승인되어 등록된 스크립트 버전 또는 에이전트 작업 정의 |
| parameters | 검증 가능한 입력. 비밀값은 참조만 저장 |
| agent_options | 에이전트 실행에만 사용하는 지시·모델 설정 |
| scopes | 읽을 수 있는 정보, 쓸 수 있는 작업 영역, 외부 행동 권한 |
| limits | 실행 시간, 모델 비용, 도구 호출 및 동시 실행 한도 |
| overlap / recovery | 이전 실행 중 재호출과 서버 재시작 시 처리 |
| output_route | 사건 저장, 브리핑 후보, 사용자 결과 등 출력 목적지 |

예시는 개념적 설정이며 완성된 설정 파일 문법이 아니다.

```yaml
id: poll-lms
trigger:
  kind: interval
  minutes: 15
executor: script
executor_ref: lms.fetch_changes@approved-version
parameters:
  connection_ref: personal-lms
output_route: source-events
```

```yaml
id: morning-briefing
trigger:
  kind: daily
  at: "07:30"
  timezone: Asia/Seoul
executor: agent
executor_ref: briefing.compose@approved-version
agent_options:
  instruction_ref: morning-briefing
  model_ref: default-economical
output_route: briefing-and-push
```

15분과 `Asia/Seoul`은 제안값이다. 모델을 쓰는 반복 작업도 같은 방식으로 등록할 수 있다.

### 5.2 선택 기준과 연결

정해진 API 조회, 커서 비교, 날짜 계산, 파일 변환, 저장과 전달은 우선 스크립트로 처리한다. 자연어 의미 해석, 모호성 판단, 조사와 종합에는 모델을 사용한다.

예: `LMS 수집 스크립트 → 변경 사건 → 필요한 경우에만 의미 해석 → 브리핑 후보 또는 긴급성 판단`.

빈번한 확인마다 전체 받은편지함이나 LMS를 모델에 보내지 않는다. 읽기 실패를 내용 변경으로 취급하지 않고, 커서는 결과 저장이 성공한 뒤 전진시킨다.

일반 산출물 파일과 실행 가능한 도구 등록을 구분한다. AI가 파일을 작성할 수 있다는 사실이 해당 파일의 운영 실행 권한을 뜻하지 않는다.

### 5.3 내구성과 실패 처리

- 예약 정의, 실행 상태, 결과와 커서를 영속 저장한다.
- 실행은 `queued / running / awaiting_approval / succeeded / failed / cancelled / interrupted`를 구분한다. 재개는 이전 시도와 연결된 새 시도로 기록한다.
- 한 자동화의 중첩 실행은 기본적으로 막고, 실행 식별키로 같은 수집·브리핑의 중복 생성을 방지한다.
- 조회 등 재실행 가능한 작업에만 제한된 재시도를 적용한다. 외부 변경의 결과가 불명확할 때 자동으로 반복하지 않는다.
- 서버 재시작 후 중단된 실행을 식별한다. 스크립트의 재개와 에이전트의 저장된 결과에서 이어가기 가능 여부를 구분하고 무조건 성공 처리하지 않는다.
- 놓친 브리핑은 회차별로 몰아서 보내지 않는다. 최신 브리핑으로 합치는 방식을 제안하며, 정확한 유예 시간은 구현 시 설정한다.
- 실제 스크립트 실행도 상태·권한·제한·로그·승인 계약을 동일하게 적용한다.

## 6. 외부 정보 연결

### Google Calendar

여러 캘린더의 일정·변경·취소·반복 일정을 읽어 개인 준비와 연결한다. 원본 식별자와 시간대를 유지한다. 초기 연결은 읽기 중심이며 생성·수정·삭제에는 별도 권한과 사용자 승인이 필요하다.

### Gmail

허용한 메일 범위에서 신규·변경 내용을 읽는다. 일정·마감·요청 후보와 뉴스레터 자료를 구분한다. 발송·삭제·읽음 처리·라벨 변경은 조회의 부수 효과로 수행하지 않는다.

### 한양대 LMS

대상은 `lxp-canvas.hanyang.ac.kr`이다. Canvas CLI를 어댑터로 사용하는 방안을 우선 확인한다. 실제 CLI 출력·인증 방식·서버에서의 사용 가능성은 구현 조사에서 검증한다.

수강 과목, 과제, 마감, 공지와 관련 자료 중 접근 가능한 범위를 연결한다. 지원하지 않는 기능을 추측으로 채우지 않는다. 제출은 초기 필수 범위에 넣지 않는다.

### 연결의 공통 계약

자격증명은 서버에 보관하고 모델 입력·대화·실행 로그에 노출하지 않는다. 읽기 범위를 설정할 수 있게 하고 연결 만료·재인증·부분 실패를 표시한다.

Google 인증과 LMS 인증의 실제 서버 경로, 접근 가능한 데이터는 아직 검증하지 않았다. 모델 제공자에게 자료를 전송하는 범위도 연결 설정에서 설명한다.

## 7. 파일 저장소와 대화

사용자는 파일을 올리고, 목록을 보고, 내려받을 수 있다. 작업의 입력·출력 파일은 대화와 실행 기록에서 찾을 수 있다. 문서 미리보기와 공동 편집은 첫 필수 범위가 아니다.

대화에서는 `/files/tasks/<task-id>/draft.md` 같은 사용자용 논리 경로를 표시한다. 실제 서버 절대 경로를 링크로 노출하지 않는다. 파일 링크는 인증을 거쳐 접근하고 저장소 밖 경로에 접근할 수 없게 한다.

에이전트는 지정된 작업 영역에 산출물을 만든다. 사용자 원본을 덮어쓰거나 삭제하는 것은 새 초안 작성과 구분하여 승인 대상으로 두는 방안을 제안한다.

채팅은 여러 대화를 보존하며 진행 중인 작업으로 돌아갈 수 있어야 한다. 대화 중 추가 지시, 취소, 승인 응답을 해당 작업과 연결한다.

## 8. 기억과 작업 상태

연구 노트의 용어를 모두 화면에 노출할 필요는 없다. 내부적으로 최소한 다음을 구분한다.

| 데이터 | 최소 보존 내용 |
|---|---|
| 원본 자료 | 대화·외부 항목·파일의 식별자, 위치, 수집 시각, 버전 |
| 기억 | 진술, 사실·선호·추론 구분, 근거, 현재 상태, 정정 관계 |
| 지속 맥락 | 관심사·진행 중인 일과 관련 기억·자료 |
| 약속·마감 | 원본 의무 또는 명시적 위임, 시각, 변경 이력 |
| 작업·실행 | 목표, 입력, 상태, 산출물, 검증 결과, 비용 |
| 관찰 조건 | 확인할 변화, 주기·조건, 허용 응답, 만료·중지 |
| 승인 | 대상 행동·변경 버전, 사용자 응답, 유효 범위, 사용 이력 |
| 브리핑·알림 | 근거, 본문, 발생·전송·열람 상태, 중복 방지 식별자 |

최신 상태뿐 아니라 무엇을 언제 알게 되었는지도 보존한다.

기억은 수정 가능한 사용자 점검 화면과 대화에서 다룬다. 모든 대화 내용을 영구적인 사용자 속성으로 만들지 않는다. 기억 추출 실패가 대화 원문을 없애거나 사용자 응답을 막지 않도록 한다.

서로 다른 출처의 충돌은 근거와 함께 보존한다. 최신 수집이라는 이유만으로 이전 확정 정보를 무조건 대체하지 않는다.

## 9. 실행 권한과 자기 개선

읽기, 내부 산출물 작성, 외부 변경, 운영 환경 변경을 별도 권한으로 다룬다. 승인에는 수행할 행동과 대상, 중요한 인자 또는 변경 버전을 담는다. 승인 뒤 내용이 바뀌면 재승인이 필요하다.

새 Skill·스크립트 등록, 기존 스크립트 교체, 하네스 코드·실행 프롬프트·도구 권한 변경은 운영 환경 변경이다. 자동 기억 갱신을 통해 이를 우회하지 못하게 한다.

사용자 승인 없이 외부 메시지 발송, 캘린더 변경, LMS 제출, 파일 외부 공유를 수행하지 않는다. 외부 자료의 문구는 사용자 명령으로 취급하지 않는다. 외부 전송 도구의 목적지·인자는 실행 단계에서 검사한다.

변경안은 작성·격리 시험·승인 대기·적용·되돌림을 추적한다. 시험이 통과하지 않은 변경을 통과한 것으로 표시하지 않는다. 코드가 적용된 뒤 필요한 재시작과 검증도 변경안에 포함한다.

기억에 의한 개인화와 운영 정책 변경의 경계: “답변을 짧게” 같은 표현 선호는 기억으로 반영할 수 있지만, 외부 권한·비용 제한·긴급 알림 허용 범위를 기억에서 임의로 넓힐 수 없다.

## 10. 브리핑과 Web Push

브리핑 원문은 서버에 먼저 저장한다. 푸시는 브리핑 또는 관련 작업을 여는 알림으로 사용한다. 정기·긴급 알림과 승인 요청을 같은 알림함에서 확인할 수 있게 한다.

기기별 구독, 구독 해제, 알림 권한 상태, 전송 실패·만료된 구독을 관리한다. 푸시 전달을 보장하거나 푸시 서비스의 접수를 사용자 열람으로 취급하지 않는다. 알림함이 수신 여부와 무관한 확인 경로다.

기본 잠금 화면 문구는 개인 내용이 드러나지 않는 짧은 안내로 제안한다. 알림을 눌러도 인증을 거쳐 원문을 확인한다.

개인적 관심 정보는 정기 브리핑에만 포함한다. 교통·출발 안내와 메신저 갈등 감지는 장기 기대이며 첫 구현의 데이터 연결 범위에는 포함하지 않는다.

## 11. 모델, 비용과 운영 기본값

공급자·모델·API Key는 서버 설정으로 교체 가능하게 한다. DeepInfra 등 API Key 기반 제공자를 초기 후보로 삼고, 사용자가 예로 든 DeepSeek V4.1 Flash 계열은 실제 호출·도구 사용·한국어 응답을 시험한 뒤 기본값을 선정한다.

모든 작업을 비싼 모델로 올리거나 기본적으로 여러 에이전트를 호출하지 않는다. 명확한 병렬 작업 또는 검토 필요가 있을 때 작업별 전문가를 사용할 수 있다. 공유 작업 기록과 산출물은 단일·다중 실행 모두에서 동일하게 유지한다.

다음은 **제안값**이며 사용자 확정값과 구분한다.

| 항목 | 제안 |
|---|---|
| 시간대 | `Asia/Seoul` |
| 수집 주기 | 일정·메일·LMS 변경 확인 15분 |
| 관심 정보 검색 | 하루 한 번, 제한된 주제·자료 수 |
| 월 예산 기준 | 달력 월 단위 USD 100 |
| 70달러 | 비용 안내 |
| 90달러 | 자율 탐색·개선 실험 축소 |
| 100달러 | 추가 유료 호출 승인 대기 |

모델뿐 아니라 유료 검색 등 시스템이 발생시키는 API 비용도 합산한다. 서버 비용과 기존 고정 구독료의 포함 여부는 미정이다.

요청 전에 예상 최대 비용을 예약하고 실제 사용량으로 정산한다. 동시 실행과 재시도도 비용에 포함한다. 가격·사용량을 알 수 없으면 0으로 처리하지 않고 추정 또는 미확인으로 표시한다.

내부 비용 제한은 공급자 청구액의 절대 보장을 뜻하지 않는다. 적용 가능한 공급자 예산 제한과 함께 사용하며 과금 차이를 확인한다. 예산 소진 시 새 유료 해석은 멈추되 저장된 브리핑·파일 조회와 비용이 발생하지 않는 수집·명확한 마감 비교는 유지한다. 최신 브리핑 생성이 중지됐다는 사실을 표시한다.

## 12. 서버 운영의 최소 조건

- 단일 사용자 인증과 HTTPS를 갖춘 PC·모바일 웹 접근.
- 모델·Google·LMS 자격증명과 푸시 구독 정보를 일반 파일 탐색·모델 도구 접근에서 제외.
- 승인되지 않은 셸 명령·생성 코드가 운영 서버 전체 권한으로 실행되지 않도록 작업 영역과 실행 권한 제한.
- 데이터·업로드 파일·작업 상태·설정의 백업과 복원 경로. 비밀값의 백업 취급은 명시.
- 연동·스케줄러·실행기·푸시의 상태와 최근 실패를 사용자가 확인 가능.
- 원문 보존·삭제와 로그 보존 정책 설정. 로그에 API Key와 인증 토큰을 기록하지 않음.

실제 서버의 운영체제·자원·도메인과 배포 방식은 확인이 필요하다. 과거 프로토타입의 배포 설정을 검증 없이 새 시스템에 적용하지 않는다.

## 13. 구현 순서와 완료 증거

순서는 제안이며 기능을 가짜 연동이나 빈 응답으로 완료 처리하지 않는다.

| 단계 | 산출물 | 완료 증거 |
|---|---|---|
| A. 실행 기반 | 인증, 대화, 모델 설정, 작업·스크립트 실행, 파일 저장소 | 실제 모델 대화, 스크립트 실행, 파일 업로드·생성·다운로드, 클라이언트 종료 후 결과 확인 |
| B. 개인 정보 연결 | Calendar·Gmail·LMS 어댑터와 변경 사건 | 허용된 실제 계정의 조회, 재수집 중복 방지, 인증 만료·부분 실패 표시 |
| C. 브리핑·푸시 | 예약, 아침·저녁 브리핑, 긴급 분류, 알림함 | 출처 있는 실제 브리핑, 대상 PC·모바일의 푸시 수신·열기, 재시작·중복·전송 실패 확인 |
| D. 기억·위임 | 자동 기억, 정정, 조사·초안 작업의 연결 | 정정 뒤 다음 답변·브리핑 반영, 실제 과제의 조사·초안과 내부 파일 접근 |
| E. 개선 변경안 | 스크립트·Skill 변경 제안, 격리 시험, 승인·적용 | 미승인 버전 실행 차단, 승인한 버전 적용, 실패·되돌림 확인 |

각 단계에서 타입·정적 검사와 해당 동작 테스트를 실행한다. 화면은 PC·모바일에서 직접 확인한다. 인증·승인은 실제 브라우저 요청 경로를 포함한다.

통합 완료 기준:

1. 실제 개인 일정과 LMS 과제, Gmail 정보를 근거로 정해진 시각의 브리핑을 생성하고 Web Push로 접근한다.
2. 마감 변경을 중복 없이 감지하고 긴급성에 따라 다음 브리핑 또는 푸시로 보낸다.
3. 브리핑의 과제 하나를 대화로 위임해 조사·초안·파일 결과를 확인한다.
4. 서버 재시작과 클라이언트 종료에도 기록이 유지되고 중단 작업이 명확히 표시된다.
5. 기억 정정이 이후 답변에 반영되고, 외부 행동과 운영 환경 변경은 승인 없이 실행되지 않는다.
6. 스크립트 수집은 모델 없이 작동하며, 모델·검색 비용과 예산 대기를 확인할 수 있다.

테스트 통과는 사용 편익의 증명이 아니다. 실제 사용에서는 놓친 변화, 불필요한 알림, 잘못된 기억, 수정 요청, 비용을 기록해 다음 변경의 근거로 삼는다.
