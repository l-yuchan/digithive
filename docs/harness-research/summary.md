# 조사 요약 — 결정을 위한 한 장

작성일: 2026-11-24. 원문: `report.md`. 상세 근거: `sources.md`, `case-studies.md`, `comparisons.md`, `architecture-options.md`, `validation.md`.

## 무엇을 했나

OmO(현재 운영 하네스), OpenCode, Codex를 지정 커밋 기준으로 조사했다. 코드·공식 문서·이슈 10건(본문·댓글)을 읽고, OmO 이슈는 문제→원인→수정→후속까지 추적했다. digithive v2 코드의 실제 상태와 대조했다. 유료 모델 호출 없이 진행했고, 위임 조사 3건은 산출물 없이 정지해 취소하고 직접 수행했다(이 자체를 관찰 사례로 기록).

## 핵심 발견 5개

1. **세 하네스 모두 "실행 코어 + 다중 표면 + 서버가 소유하는 세션 + 커서 이벤트 재생"으로 수렴했다.** digithive는 이미 절반을 갖고 있다(서버, SQLite, seq 이벤트 재생). 빠진 것은 라이브 스트리밍, 메시지 part 구조, 대화 관리, 현재 시각 주입이다.
2. **진짜 위험은 기능 부족이 아니라 "정산되지 않는 상태"다.** OmO에서 반복된 결함은 영구 `running`, 데드라인·abort 부재, 거부를 결과로 안 돌려줌, 파일 연산에 걸린 상태, 진입점마다 다른 정책 해석이다. 하네스를 바꾸든 말든 digithive가 먼저 갖춰야 할 목록이다.
3. **두 역할(대화 / 백그라운드 작업)은 공통 코어 + 역할별 실행 계층이 근거상 우세하다.** 세 제품이 독립적으로 같은 분리를 택했다. 대신 OmO식 복잡한 상태 기계(parking/부활/팀 mailbox)는 1인 유지에 과하다.
4. **OmO 채택은 작업 역할에만 현실적이다.** 라이선스는 Sustainable Use(개인 사용 허용, 재배포 제한). 대화 표면은 코딩·터미널 어휘와 승인 피로 때문에 부적합. OpenCode는 MIT이고 구조가 가장 가깝지만 코딩 에이전트다.
5. **UI는 렌더러보다 "스트리밍·메시지 트리·도구 기록을 누가 소유하는가"가 결정 변수다.** React + 채팅 런타임(assistant-ui 또는 AI SDK UI)이 방어적이나, 이는 상세 계획에서 확정해도 늦지 않다.

## 지금 바로 고칠 수 있는 것 (조사와 무관하게 명확)

- 시스템 프롬프트에 `Asia/Seoul` 현재 시각 주입 → "날짜를 메일에서 추론" 문제의 직접 원인.
- 한국어 IME 조합 중 Enter가 전송되지 않게, Shift+Enter는 줄바꿈, 초안 보존.
- 대화 제목 표시·변경(현재 제목이 "대화"로 고정).

## 승인이 필요한 결정

| # | 결정 | 권고 |
|---|---|---|
| 1 | 두 역할 구조 | 공통 코어 + 역할별 실행 계층(C) |
| 2 | 작업 역할에 OmO 유지 여부 | 현행 유지(작업만), digithive 쪽에 리스·정산 래퍼 추가 |
| 3 | UI | React + 채팅 런타임 (상세 계획에서 확정) |
| 4 | 상세 계획 범위 | 대화 경험(스트리밍·part·대화 관리)부터 |

구현·배포는 이 요약에 대한 승인 이후 별도 계획으로 진행한다. 이번 조사는 코드도 배포도 건드리지 않았다.

후속: 사용자 결정(공통 코어+실행 계층, OmO 미사용·직접 구현, React, 전면 rewrite)을 반영한 상세 구현 계획은 `.omo/plans/digithive-harness-rewrite.md`에 있다.

## 남은 불확실성

- 세 하네스의 실제 실행 비교는 하지 않았다(설치·구동 없음).
- Codex 컨텍스트 조립, OpenCode 저장 스키마 세부는 근거가 얕다(위임 실패 영향).
- OmO 수정이 현재 설치본(5.1.65)에 반영됐는지 미확인.
- UI 후보의 한글 IME·모바일 실측 없음.
