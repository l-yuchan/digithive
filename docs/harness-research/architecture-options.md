## 1. 책임·소유권 표

모듈을 폴더 이름으로 나누지 않고, "무엇이 무엇을 소유하는가"로 먼저 정리한다.

| 책임 | 소유하는 것 | 의존해도 되는 것 | 의존하면 안 되는 것 |
|---|---|---|---|
| **도메인 규칙** | 대화·메시지·작업의 상태 전이, 승인 정책 결정, 예산 규칙 | 스키마 | HTTP·UI·모델 SDK |
| **실행기(executor)** | 한 작업의 루프(모델 호출 → 도구 → 결과) | 도메인 규칙(판정 요청), 모델 어댑터, 도구, 이벤트 기록 | HTTP 요청 객체, 웹 클라이언트 |
| **모델 어댑터** | 공급자 요청/응답 변환, 스트림 파싱, 오류 분류, 사용량 | 없음(순수 경계) | 상태 저장, 정책 |
| **이벤트·API** | 정규 이벤트 로그(seq), 커서 재생, 클라이언트 전송, 승인 요청 전달 | 도메인 규칙(조회), 실행기(기록) | UI 렌더링 |
| **저장** | 세션·메시지 트리·작업 레코드·이벤트·예산 | 스키마 | 도메인 판단 |
| **웹 클라이언트** | 렌더링, 입력, 로컬 초안 | 이벤트·API 계약 | 실행기, 저장, 모델 |

의존 방향은 위에서 아래로만: **도메인 ← 실행기 ← (어댑터, 도구)**, 그리고 **이벤트·API는 도메인과 실행기의 기록을 읽기만** 한다. 클라이언트는 API 계약만 안다.

세 하네스의 실제 배치(비교 근거):
- OpenCode: `Schema → Core/Protocol → Server`, 클라이언트는 `Schema/Protocol`까지만 import 가능(저장소 `AGENTS.md` 규칙).
- Codex: `protocol` 크레이트가 계약, `core`가 실행, `app-server`가 전송.
- OmO: `senpi` 엔진이 실행·세션·이벤트를 소유하고, OmO 플러그인이 도구·정책·위임을 얹는다.

digithive 현재 매핑: `contracts/`(스키마) → `agents/`(모델) + `runtime/`(큐·예산) + `server/routes`(API) → `web/`(클라이언트). **아직 도메인 규칙 계층이 없다.** 판정이 라우트 핸들러와 실행기에 흩어져 있다.

## 2. 세 대안의 흐름

### A. 하나의 하네스 공유 (OmO 방식)
```
사용자 → 세션(대화 턴) → task 도구 → 자식 세션
                          ↘ 완료 알림(부모 상태별 주입)
```
- 위임 시: 목표·프롬프트·모델 카테고리·권한·격리 모드·실행 모드(in-process/process).
- 이벤트: 자식 이벤트는 부모 대화에 요약 주입, 원본은 자식 트랜스크립트.
- 복구: parking/revival, 완료 라우팅, 취소는 동기 결과.
- 관찰된 비용: 정산·취소·재개 상태 기계가 크고, 실패 계열이 반복된다(`case-studies.md` C1·C2·C7).

### B. 완전히 별개 하네스
```
대화 하네스 ⇄ (사용자가 복사/붙여넣기 또는 커스텀 브리지) ⇄ 작업 하네스
```
- 이점: 양쪽 독립 배포, 장애 격리.
- 비용: 인계·승인·결과 연결을 매번 새로 만든다. digithive는 이미 "run"이라는 공통 개념과 예산·기억을 공유하므로, 별개 하네스는 **같은 데이터를 두 번 모델링**하게 된다.

### C. 공통 코어 + 역할별 실행 계층 (권고)
```
        ┌──────────── 공통 코어 ────────────┐
        │ 도메인 규칙 · 이벤트 로그 · 저장 ·  │
        │ 모델 어댑터 · 도구 계약 · 예산      │
        └───────┬───────────────┬───────────┘
                │               │
   대화 실행 계층(빠른 턴)    작업 실행 계층(긴 루프, 격리, 검증)
   - 도구: 조회·승인요청 중심   - 도구: 쓰기·실행·검증
   - 응답 목표: 수 초           - 목표: 완료 조건 + 증거
                │               │
             웹/모바일         스케줄·브리핑·재시도
```
- 코드 공유: 도메인·이벤트·저장·어댑터. 실행 인스턴스: 세션·큐·프로세스·권한·예산 분리.
- 위임 시 전달: 목표, 입력 자료(출처 id), 권한 프로필, 예산 상한, 완료 조건.
- 이벤트: 하나의 정규 로그(seq)에 `run_id`, `parent_run_id`, `kind`. 대화 클라이언트는 자기 run의 이벤트만, 상세 화면은 전체를 본다.
- 복구: run마다 리스(heartbeat). 리스 만료 → `interrupted`로 정산하고 재개 가능 여부를 기록.

**선택 이유** (근거 기반):
1. 세 하네스가 독립적으로 같은 형태로 수렴했다 — 이건 취향이 아니라 압력의 결과다.
2. digithive의 실패 위험이 OmO 사례에서 확인된 **정산·취소·재개 상태 기계**에 집중되므로, 코어를 하나로 두고 그 상태 기계를 한 곳에서만 관리하는 편이 낫다.
3. 대화 역할에 전체 도구 집합을 주면 승인 피로·지연·맥락 오염이 생긴다(OmO가 이 문제를 프롬프트·프리셋으로 완화하지만 근본 해결은 역할 분리).

**선택하지 않은 이유**:
- A는 이미 검증된 힘이 있으나, digithive가 그 복잡도를 유지할 인력이 1인이다.
- B는 장애 격리는 최고지만 인계 비용이 매번 새로 든다.

## 3. 권고 구조의 경계 (개략)

| 구성 요소 | 유지 | 교체 | 비고 |
|---|---|---|---|
| 서버·라우팅(Bun) | 유지 | — | 이미 최소·동작 |
| 저장(SQLite) | 유지 | 스키마 확장 | 메시지에 part 구조 추가 필요 |

| 시스템 프롬프트 조립 | **교체·확장** | 날짜·시간대·도구·기억 순서 | 현재 날짜 없음 |

| 기억·파일·연동 | 유지 | — | 이미 제품 고유 가치 |

## 4. 대안별로 남는 위험

| 위험 | A | B | C |
|---|---|---|---|
| 정산 안 됨(영구 running) | 높음(사례 다수) | 중간 | **중간** — 리스 규약이 관건 |
| 승인 우회·침묵 거부 | 높음(#14649) | 중간 | 낮음(거부를 결과로 강제) |

| 되돌림 비용 | 높음(포크·엔진 교체 사례) | 낮음 | 중간 |

## 5. 설계 체크리스트 (사례에서 추출)

새 구조가 갖춰야 할 것 — 각 항목은 `case-studies.md`의 실패 계열에 대응한다.

1. **모든 턴·도구·훅에 데드라인**과 abort 전파 (C3, C4). 결과는 "타임아웃"으로 정산되고 턴은 계속된다.
2. **상태 정산 규칙**: 종료 이벤트가 오지 않으면 리스 만료로 `interrupted`. `running`은 리스가 살아 있을 때만 (C1, C6).
3. **거부도 결과**: 정책 거부는 구조화된 도구 결과 + UI 상태 + 정상 턴 종료 (C5).
4. **취소 의도 구분**: `user_cancel` / `host_restart` / `interrupted` / `timeout` (C7).
5. **상태 전이는 재조정 가능하게**: 파일 rename 같은 단일 연산에 영구 상태를 걸지 않는다 (C2).
6. **정책 해석은 한 곳**: 진입점(웹·스케줄·스크립트)마다 해석기가 다르면 우회된다 (#13016).
7. **프롬프트 정책은 매 턴 재주입**: 압축·도구 다발 턴 이후 표류 방지(C8). 날짜·시간대도 같은 방식.
8. **가시성은 3단**: 시작/종료 + 중간 진행(도구 호출·부분 출력) + 상세(원본 트랜스크립트) (C9).

## 6. 이행·되돌림

- **데이터**: 메시지 테이블에 part 구조를 추가하는 마이그레이션은 기존 `content`를 text part 1개로 승격하면 된다. 기존 대화는 그대로 읽힌다.
- **병행 운영**: 새 클라이언트를 `/app2`에 두고 2주 병행하는 방식이 가능하다. 서버 계약은 추가만 하고 제거하지 않는다.
- **되돌림 지점**: 모델 어댑터(스트리밍)와 클라이언트가 독립적으로 되돌릴 수 있어야 한다. 세션 파일 포맷은 OmO처럼 한 번에 갈아엎으면 되돌리기 어렵다(#7728 사례).

## 7. 후속 상세 계획에서 정할 것
- 대화 턴과 run의 관계(1:1인지 1:N인지), 위임 도입 시점.
- 스트리밍 전송 방식(SSE vs WebSocket)과 재연결 계약.
- 메시지 part 스키마와 편집·분기 시 원본 보존 규칙.
- UI 프레임워크·런타임 확정(§5 비교 기준으로 결정).
- 도구 집합과 승인 프리셋, 예산 축(일/작업/모델).
